### Changed
- Package metadata for npm: `publishConfig.access` is `public`; `sideEffects` is `false` (no module does anything when imported, so bundlers can leave out the unused ones); `repository.url` has the `git+https` form that provenance is checked against; `author` is written as in `LICENSE`. Source maps now embed their TypeScript sources (`inlineSources`) and declaration maps are no longer built: both pointed to `src/`, which is not published. The package holds `dist/` (JavaScript, declarations, source maps), `README.md`, `LICENSE`, `CHANGELOG.md` and `package.json`.
- **Cognitive runs can fail on a policy.** A cognitive agent under a budget or timeout policy (its own or a global one) now stops when the policy's limit is reached, with `status: 'failed'`, where it used to go on until its own `limits`; each step's check is in the policy audit trail (a `policy.checked` event for each budget or timeout policy that can apply to a step). Budgets per period now also count cognitive agents' and `sdk.decisions` calls (see Fixed), so a limit that names no agent is spent sooner, and a `maxCost` limit that names no agent refuses every agent's tool calls, and cognitive steps, as soon as one of these calls has a model without a price (only Jev is priced by default) or reported no token counts. A replay of a cognitive run recorded before this version gives its tool calls the original run's progress too: a call the original run made may now be refused by a run limit. **Migration:** give every model your agents use a price in `SDKConfig.pricing` — LLMs, and the model a custom typed-decision backend reports — or name the agent in cost limits (`agentId`); to end a cognitive run with a decision, keep `limits.maxSteps` within the policy's `maxSteps`. Public API: `PolicyEngine.validateRunStep(context)`, which checks the budget and timeout policies before a step; `PolicyEngine.recordModelUsage(agentId: string | undefined, { model?, requestedModel?, usage?, calls? })` takes an `agentId` of `undefined` (counted only by limits that name no agent) and the number of model `calls` behind one usage (a whole number above 0, else 1); `CognitiveAgentEnvironment` and `CognitiveAgentDependencies` take an optional `policyEngine`, and `DecisionService` an optional third argument, the budgets its calls count in.
- **The `SDK` interface has a new required method, `subscribe`, and `replay` takes a third parameter** (`{ onEvent }`): a class of your own that implements `SDK` (a test fake, for example) no longer compiles until it adds them. Classes that implement `IEventStore` or `GovernedToolHost` are unaffected: `subscribe` and `onEvent` are optional there.
- `isTransientError` retries an OpenAI or Anthropic API error sent in the middle of a stream, which has no HTTP status, as its HTTP counterpart: OpenAI `server_error` and Anthropic `rate_limit_error`, `api_error`, `timeout_error` and `overloaded_error` are transient, other types are not. A connection closed in the middle of a streamed answer (`ERR_STREAM_PREMATURE_CLOSE`) is a connection failure.
- **`runRegressionTests` and `runRegressionTestsForCI` return every suite.** They return a `RegressionTestRunResult` (the totals and `suites`, one `RegressionTestSuiteResult` per suite, oldest first) instead of the result of the first suite; `exportTestResults` accepts either (JUnit: one `<testsuite>` per suite; JSON: `suites`). `RegressionTestSuiteResult.agentId` is the agent that ran the tests, not the one that created the suite. `createRegressionTestSuite` takes an agent of this SDK by id or by name (a name two agents share is refused) and checks each golden trace and input (`ValidationError`). `getGoldenTraces`, `getRegressionTestSuites` and `getAssertions` accept an agent's id or name. Within one SDK an agent's id is its own: two agents with the same name (two versions) keep their own suites, assertions and golden traces; by name, or from another process, the artifacts of every agent of that name are found. Migration: read the tests in `results.suites[i].results` (`results.results` was the first suite's); create the agent before `createRegressionTestSuite`, which throws for an agent that is not in the SDK; JUnit suite names become `Agent Regression Tests - <agent name> - <suite name>` and test case names the test's `name` (the golden trace id before), so CI tools start a new history.
- **Advanced filters have a scope and conditions.** `runId`, `since` and `until` choose the events looked at; `type`, `agentId`, `userId`, `sessionId`, each data filter and each metadata filter are conditions, combined with `logic` and then negated by `not`. `logic: 'or'` used to apply only among the data filters and among the metadata filters, and-ed with everything else; `not` negated the scope too. `AdvancedEventQueryResult.total` is the number of events in scope, on every store (it was the number the store happened to return). `limit` must be a whole number ≥ 0 (`limit: 0` returns no event; a fractional or negative limit throws a `ValidationError`). Events are in time order on every store, and events of the same millisecond keep the order of their run: runs by id, then as each run recorded them (SQLite orders by `timestamp, run_id, rowid`, PostgreSQL by `timestamp, run_id, seq`, the file store by run and position). Migration: `type = X AND (A OR B)` can no longer be one filter; query `{ type: X, logic: 'or', dataFilters: [A, B] }` gives `X OR A OR B` — filter the type afterwards, or run two queries.
- **Comparison options.** Timing is compared only with `tolerance.timestampMs`, relative to the start of each run (absolute timestamps with a 0 ms tolerance by default before); a run's duration is checked only with `maxDurationDiff` or `severityThresholds`, and only a slowdown regresses; `maxEventCountDiff` tolerates up to that many added or removed process events (policy checks, retries, approvals), never a change of the result; `detectRegressions` reports `regressions_detected` whenever a regression remains. A validation is `partial` only when `compareStructureOnly` is set and every difference is a data difference: `ignoreTimestampDiff` turned every modification into `partial`, and a structure-only comparison lowered a changed event type, a move or a timing difference too. `ComparisonOptions.groupSimilarEvents` and `ImpactAnalysisOptions.groupBy` are marked deprecated: they never had an effect. The `cost` metric of `analyzeImpact` is named `cost (usd)` (see Fixed).
- **PostgreSQL event tables get a `seq BIGSERIAL` column**, the order events were appended in: `getEvents(runId)` orders by `timestamp, seq` and `queryEvents` by `timestamp, run_id, seq`, where events of the same millisecond came back in no guaranteed order (their ids are random). The store adds the column to a table created by an earlier version when it starts (`ALTER TABLE … ADD COLUMN IF NOT EXISTS seq BIGSERIAL`, only when `information_schema.columns` does not list it, so PostgreSQL 12 and earlier create no unused sequence at each start); PostgreSQL then rewrites the table once, under a lock: on a large table, start the new version when that is acceptable. SQLite orders the same ties by `rowid`. `backup()` lists the events in the order of `queryEvents`, so `restore()` keeps each run's order (a backup ordered by time only could scramble events of the same millisecond, and on PostgreSQL `seq` then kept that order); on PostgreSQL, `backup()` no longer throws on the JSONB columns node-postgres has already parsed.
- **Policies are checked when they are applied.** `createSDK({ defaultPolicies })`, `defineGlobalPolicy`, an agent's `policies` (`createAgent`, `createCognitiveAgent`) and `agent.setPolicy` throw a `ValidationError` naming the field (`Validation failed: policy 'caps' rules[0].metadata.budgetLimit.maxToolCalls - must be a finite number >= 0, got NaN`) before anything is registered, when a limit cannot be checked: a `maxSteps`, `maxTokens` or `maxDuration` `value` that is not a finite number above 0 (`NaN`, `0` or a missing value turned the limit off, `Infinity` meant no limit and a negative value refused every call; a numeric string such as `'10'` worked only by coercion); a limit in a policy type that never reads it (`maxDuration` outside a `timeout` policy, `maxSteps`, `maxTokens` or `budgetLimit` outside a `budget` one), which did nothing; a `budgetLimit` without a known `period`, without any cap, with a non-string `agentId` or `toolName`, or with a cap that is not a finite number ≥ 0 (`NaN` turned it off, `Infinity` meant no cap, `null` acted as 0, a string such as `'2'` lost the protection against concurrent calls); a policy that is not an object, or `rules` that are not a list of objects. Disabled policies are not checked, and the rules of `custom` and `allowlist` policies are not read as limits. A limit changed after its policy was applied, and no longer checkable, refuses the calls it covers; a `budgetLimit` removed from its rule, or whose `agentId` or `toolName` is no longer a string, refuses every tool call its policy is checked for. **Migration:** convert values read from the environment (`Number(process.env.MAX_STEPS)`), and remove a rule or set `enabled: false` instead of a value of `0` or `Infinity`.
- SQL event stores refuse a table name that is not an SQL identifier (ASCII letters, digits and `_`, at most 63 per part, optionally after a schema: `app.events`), since it is written into the SQL; quoted names such as `"my-events"` are refused. Indexes are named `idx_<table>_…` without the schema: with a schema-qualified table they could not be created before (SQLite ignored the failure, PostgreSQL's failure stopped the process). For subclasses: `initializeSchema(connection)` receives the connection to create the schema with; an override written for the old hook still works (queries made through `this.connection` during schema creation do not wait for it).
- The default Anthropic model is `claude-opus-5` (`claude-3-5-sonnet-20241022` is retired).
- **The default OpenAI model is `gpt-5.4`** instead of `gpt-4`, a legacy model that OpenAI shuts down on 2026-10-23. It is the model of an OpenAI fallback that does not serve the agent's model (failing over from Claude, for instance) and of a request that names none. `gpt-5.4` is current, on OpenAI and Azure OpenAI alike, and a reasoning model: it gets no `temperature`, and `maxTokens` as `max_completion_tokens` (see *OpenAI reasoning models get the parameters they accept*). It calls tools through Chat Completions, which the SDK uses, only with its default effort, `none`: a `reasoningEffort` other than `none` makes OpenAI refuse the requests of agents with tools. Set `providerConfig.openai.defaultModel` (or a fallback's `config.defaultModel`) to keep another model; `DEFAULT_OPENAI_MODEL` is exported. A `ReasoningEngine` created without a model lets its provider use its own default model instead of asking any vendor for `gpt-4`.
- Public types: `SDKConfig.fallbackProviders` items are a union on `provider` (an OpenAI fallback's `config` also takes the OpenAI options); `providerConfig.openai` is an `OpenAIVendorConfig` and `providerConfig.anthropic` a `VendorConfig`; `providerSettings.openai` (agents, runs, cognitive agents, `ReasoningContext`) is an `OpenAIProviderSettings`; `LLMRequest`, `CognitiveAgentConfig` and `LLMThoughtGeneratorOptions` have an optional `reasoningEffort`; `OpenAIProvider.nativeToolMessages` is a `boolean` set by its options (it was the literal `true`).
- `createSDK` refuses a fallback of another vendor that has no API key (`ValidationError` naming `fallbackProviders[i]`) instead of sending it the primary key.
- A policy refusal carries the violated policy's own reason for every policy type (a custom policy's reason included) instead of "Violated policies: <ids>".
- With fallbacks configured, `intention.generated` metadata names the provider that answered (`anthropic`) instead of "openai (fallback: anthropic)".
- `OpenAIProvider.supportsModel` also accepts `o3`, `o4-mini`, `chatgpt-*` and fine-tuned `ft:` models.
- Public types: `LLMRequest.messages` is `LLMMessage[]`, with assistant `toolCalls`/`vendorContent` and a `tool` role (only sent to providers that declare `nativeToolMessages`); `LLMResponse.toolCalls` items may have an `id`, and `LLMResponse` may carry `vendorContent`; `ActionContext` has an optional `run` (`RunProgress`: step, tokens used, start time); `LLMMessage` and `LLMToolCall` are exported.
- Tests: no suite mocks a module or a function any more. The OpenAI and Anthropic adapters, the SDK and the reasoning engine run against a local server answering in the vendor's format, event stores are real, and `no-mocks.test.ts` refuses `vi.mock`, `vi.fn` and `vi.spyOn`.
- `metadata.requiresApproval: true` on a tool is now **enforced**: every call waits for `sdk.approveAction` (policy id `tool-requires-approval`) even when every policy allows it. It was only descriptive before, so a tool marked this way ran without any approval. A replay repeats without asking only the calls a human approved in the original run (same tool, same parameters); any other such call — rejected, cancelled or never approved — is refused (policy approvals still apply).
- Pending approvals no longer wait forever. A pending approval is cancelled — the action refused, recorded as `approval.rejected` with a `reason` — when the caller's `signal` aborts (a stopped run, an MCP client that cancelled, a stdio client that exited, an HTTP connection that closed) or after `approvalTimeoutMs` without a decision (`executeTool` option; **50 000 ms by default for MCP servers**). A stateless HTTP server cannot see a client's cancellation: there, an approval lasts until the connection closes or `approvalTimeoutMs`, and a "yes" given before that still runs the tool. The call is checked again after the approval, before the tool runs. A cancelled approval fails the call with a `PolicyViolationError` instead of a raw error.
- The order of the checks of a tool call is now: allowlist, **arguments** (the tool's schema), policies, approval, budget, then the tool. Invalid arguments were checked last, after policies and approvals.
- **Call budgets are counted when a call is admitted**, checked and counted in one synchronous step, so concurrent calls cannot all get under a limit (10 of 10 simultaneous calls ran with a limit of 2). A call counts whatever its outcome, failures included; calls were counted after success only.
- Budget limits that name only an agent (or only a tool) now deny calls beyond their limit: they never counted any call before (see Fixed).
- **A governed agent only runs its own tools** (`tools`, `capabilities`): a tool registered in the SDK for someone else (an MCP server, another agent) is refused as `allowed-tools`, even if the model names it. It could run before.
- `createSDK()` without any model key no longer throws: tools and MCP servers work, and the first call that needs a model fails with "no language model is configured".
- `GovernedToolHost` (what `createMcpServer` needs from the SDK) also requires `defineTool` and `traceResourceRead`; `createSDK()` implements them. Existing `createMcpServer`/`serveMcpOverStdio` options are unchanged; `serveMcpOverStdio` writes one "ready" line to stderr and closes when stdin ends.
- Public types: the new event type `resource.read` (an exhaustive `switch` over `EventType` needs a new case); `ToolRegistry.executeTool` takes a fourth argument, the call context; `ToolDefinition.handler` a second one.
- The file event store's flush timer no longer keeps the process alive; pending events are written just before the process exits, in one attempt (a store that cannot write — its folder cannot be created — no longer keeps the process spinning). A script or a stdio MCP server can now end without `process.exit()`.
- `ApprovalManager` forgets decided requests beyond the last 1 000 (they stayed in memory forever), and keeps them out of the pending list.
- The golden-trace, regression-suite, assertion and impact-analysis folders are created when first used, not when the SDK starts: an MCP server started from any working directory no longer creates (or fails to create) them there.
- CI runs on Node.js 20.x, 22.x and 24.x; the SQLite suite runs where `node:sqlite` exists and says why it is skipped on Node 20.
- The conclusion guard can commit a **choice of action** the thinker clearly prefers (`preferenceFit` ≥ `decisionThreshold`) when its evidence support reaches `limits.minProposalSupport` (0.35): with a real thinker profile, questions such as "would you take this job?" always ended in an abstention because they have little evidence to weigh. Claims about the world (rules, explanations) still need evidence support ≥ `decisionThreshold`. The rule is recorded in `cognition.started` (`commitRules.minProposalSupport`); runs recorded before keep the evidence-only rule.
  - Public types: `CognitiveLimits` has a new field `minProposalSupport`, and `DecisionBlocker` a new variant `low_fit` (an exhaustive `switch` over blocker kinds needs a new case).
  - `minProposalSupport` may not exceed `decisionThreshold` (`ValidationError`); set it equal to switch the path off. Lowering `decisionThreshold` without setting it lowers the default floor with it.
  - The model is told that a statement about what is true is never a `proposal`, since the kind now decides which commitment rule applies, and, first of all, that when the goal asks what to do, how to react or which action to take, the hypotheses are the candidate courses of action and must cover the answer the thinker would give. With a real model and a real thinker profile, the hypotheses for "would you take this job?" were statements ("the systems could be modernized"), so no answer could be committed even when the rationale said "I decline"; with this instruction, two of three such questions ended committed instead of none.
- The documentation says plainly that a cognitive agent can imitate the way a given person reasons, and what that covers: the thinker profiles guide explains each step, where the profile weighs and where it never does, and how to measure how close the imitation gets. A new page, *Key terms in plain words*, explains every term used in the documentation.
- **Run costs: public types and events changed** (see *Run costs no longer report $0* and *Billed calls whose step fails are counted* in Fixed).
  - `DecisionResponse.usage` and `DecisionEvaluationRecord.usage` are optional: absent when the backend reported no token counts, where `JevClient` returned 0 input and 0 output tokens. **Migration:** read `response.usage?.inputTokens`.
  - `decision.evaluated` can now record a rejected answer, from `sdk.decisions` and from cognitive agents: `error` is set and `answers` is empty. **Migration:** code that reads `data.answers.*` of these events must skip those with `data.error`.
  - `EventType` has a new member, `provider.answer_discarded` (an exhaustive `switch` over `EventType` needs a new case).
  - A line of `RunCostReport` whose calls all reported no token counts has no `costUsd` (it had `costUsd: 0` when they reported a total alone). The lines are one per model, model asked for and source: calls of one model asked for under different names, or under none, are on lines of their own.
  - New fields: `RunCostReport.unpricedCalls`, `unmeteredCalls` and `unmeteredModels`. New optional fields: `ModelCostLine.unmeteredCalls`, `ModelUsage.unmeteredCalls`, `GeneratedThought.discarded` and `ThoughtGenerationError.discarded` (answers a provider discarded, which the engine records as their own events), `DecisionEvaluationRecord.error`, `DecisionClientError.billed` (`BilledDecisionCall`), `LLMRequest.onDiscardedAnswer` (`DiscardedAnswer`, with an optional `requestedModel`), `ModelCostLine.unmeteredTokens` and `ModelUsage.unmeteredTokens` (tokens of the unmetered calls) and `ReasoningContext.onModelUsage` (`AnsweredModelCall`). A governed agent counts a model call in its budgets and its run's tokens as soon as the vendor has answered, before the answer is read, through `onModelUsage`.

### Fixed
- **A policy's refusal wins over another policy's approval.** When a `require_approval` rule and a refusing policy (a deny rule, an allowlist, a token or cost budget) both matched a call, `PolicyEngine.validate` returned "approval required" and dropped the refusals: once a human approved, the tool ran, whatever the refusing policy said. A refused call is now refused, and no approval is asked; only a call no policy refuses waits for one. A tool's own `requiresApproval` was already checked after the policies. **Behaviour change:** a limit rule whose action is `require_approval` (an allowlist, budget or timeout rule) refuses once its limit is passed instead of asking a human to go over it: a spent token or cost cap refuses (a spent call-count cap was already refused right after the approval), and in an allowlist policy with an `allow [a]` rule and a `require_approval [b]` rule, `b` is refused (that setup never allowed `a` either, since every `allowedTools` rule restricts on its own). To let a human approve past a limit, put the approval in a policy of its own and leave the limit out of it.
- **A study's guardian no longer reads the charter's needs as the only allowed topics.** In a real GPT-5.4 study of the browser, it refused four security items (a security model beyond the origin, auditable and delegable powers) because security was not among the needs, though it serves the redesign. The guardian is told that the needs are priorities, not a closed list: an aspect of the object the charter does not name is on the objective when it serves the redesign; what serves another goal (a launch plan) is still off it. The reminder's out-of-scope line and the charter's needs heading say the same. Studies guide (11 languages).
- **A study keeps an item whose category is not in its list.** A real GPT-5.4 study named a historical factor `accessibility` and a combination's change `trust`: the whole item was refused for its label and logged as drift, though it served the objective. A historical factor, a combination's change, an independent lead's kind or a candidate capability's principle the list lacks is now read as `other`; blank labels are left out and a category named twice is kept once. A combination can change `trust` and `verification` (`StudyChangeKind`), as an architecture's principle can. The principle a capability architecture changes still has to be one of the list: "none" or "speed" is refused, never read as `other`.
- The test suite runs each file in a child process (`pool: 'forks'` in `vitest.config.ts`, Vitest's default from version 2) instead of a worker thread, where `process.env` is a copy per thread: a full run once crashed Node 24 with a segmentation fault (`node::MapKVStore::Set`) while a test restored `OPENAI_BASE_URL`. That test, which proves a same-vendor fallback does not inherit the primary's gateway, now sets the variable only around the synchronous `createSDK` call that reads it.
- Tests no longer write into the working tree nor read what earlier runs left there. The suites that used the SDK's default event store (`./events`: decision patterns, alternatives, reasoning graph, trace visualization, policy audit trail, budget tracker, the benchmarks and the starter template's test) or a shared folder (`./test-events` for the action and replay engines, `./test-events-<time>` for the file event store) each use their own temporary folder: the decision-pattern test analysed every run found in `./events`, so its result depended on leftovers, and three suites appended to the same run ids at the same time. The file event store test waits for `destroy()` before removing its folder.
- **Budget and timeout policies apply to cognitive agents.** A cognitive agent's tool calls were checked with step 0, 0 tokens and a start time of "now", as governed agents' were before, so `maxSteps`, `maxTokens` and `maxDuration` never refused anything in a cognitive run, whether the policy was given to `createCognitiveAgent` or was global (allowlists, approvals, custom policies and call budgets did apply to its tool calls). A cognitive run now gives each tool call its progress — the steps it completed, the tokens of its model calls (thoughts and their repairs, tool selections, typed decisions) and its start time — and its budget and timeout policies are also checked before each step, before any of the step's model calls, against that progress and against the token and cost budgets per period (`budgetLimit` with `maxTokens` or `maxCost`, without `toolName`). A refused step is recorded as `policy.violated` (with `intention: { type: 'continue' }` and the `step`), then `run.failed` with the policy's reason, and `think` returns `status: 'failed'` with a `PolicyViolationError`; a tool call refused by a run limit is a failed operation, and the next step is refused. A step is checked as an intention of type `continue`: a policy whose conditions need a tool call applies to tool calls only, and so do a `budgetLimit` that names a tool or another agent or caps only calls, and a limit rule whose action is `require_approval` (a step never waits for an approval). The agent's own `limits` work as before. Custom policies and conditions reading `currentStep`, `tokensUsed` or `startTime` get the run's values in cognitive tool calls too. A replay gives each tool call of a cognitive run the progress of the original run at that call, so a call a run limit refused is refused again.
- **Cognitive agents' and `sdk.decisions` calls count in budgets per period.** Token and cost budgets counted only governed agents' model calls: a cognitive agent's thoughts (repairs and failed attempts included), tool selections and typed decisions, and the typed decisions made with `sdk.decisions`, were priced by `getRunCost` but spent no budget. Budgets now count every model call `getRunCost` reads, as it reads it — for its agent and for limits that name no agent; an `sdk.decisions` call for the `agentId` it names, if any — the billed calls whose step fails included: answers a provider discarded (on a thought or a tool selection), tool arguments that are not valid JSON, operations a stop or a timeout cut short after billed attempts, typed-decision answers that were rejected. A call that reported no token counts (a thought's included, whose `usage.unmeteredCalls` says how many) is a call whose cost is unknown, never $0, so a `maxCost` limit refuses rather than guess; a thought and its repairs count as that many calls. The run's `maxTokens` counts the same calls, and a replay counts them as the original run did. A budget never refuses a call of `sdk.decisions`: it refuses tool calls and cognitive steps.
- **Reasoning graphs, alternatives and decision patterns read the policy checks the SDK records.** `getReasoningGraph` and `getAlternatives` read an `allowed` field that no `policy.checked` event of the SDK has, so every check was shown as denied, and counted as a rejected alternative when an intention preceded it by less than 2 s; `getDecisionPatterns` read a `rule` field they do not have either, so no refusal by a policy ever made a violation pattern. They now read the action engine's verdict (`validation`) and the policy engine's event for each policy (`applied`); a refused tool call is one rejected alternative, not one per event. A violation pattern counts each refusal once per policy (the policy engine's event), not again for the call's verdict. Events in the flat shape (`rule`, `allowed`, `requiresApproval`) are read as before.
- A replay reads an event its store returned twice once: a tool call recorded twice ran twice.
- A governed agent's answer is counted in its budgets before the answers its provider discarded are recorded: when the store could not record them, the answer that followed was left out of the budgets. When the store cannot record a discarded answer (after the provider failed) or a rejected typed-decision answer, the SDK now says so with `console.warn` instead of dropping the store's error silently; the caller still gets the provider's or the decision client's error.
- **OpenAI reasoning models get the parameters they accept.** The o-series (`o1`, `o3`, `o4-mini`…) and GPT-5 and later refuse `max_tokens`, and `temperature` unless their reasoning effort is `none`, with a 400, and the SDK sent both on every call (a governed agent sends a temperature of 0.7 by default, a cognitive agent 0.4): agents failed on these models, except GPT-5.1 to GPT-5.4 without `maxTokens`, whose default effort is `none`. The OpenAI provider now recognizes them by name, whatever the letter case, dated or fine-tuned (`ft:o4-mini-…`) included, and sends them `maxTokens` as `max_completion_tokens` (which also counts their reasoning tokens). As the default effort varies by model, it never sends them a temperature: the temperature of the agent or of the engine is ignored for them. Other models keep `temperature` and `max_tokens`: OpenAI accepts `max_tokens` for them, and it is the parameter every OpenAI-compatible server (Azure OpenAI, local model servers, gateways) knows, where `max_completion_tokens` could be ignored and the limit silently lost. A name that says nothing, such as an Azure deployment, is declared with `reasoningModels` (see Added). A limit remains, which the SDK does not work around: on Chat Completions, which it uses, GPT-5.4 and later call tools only with the effort `none`, so an agent with tools on GPT-5.5, GPT-5.6 or GPT-6 Sol and Luna (default effort `medium`) needs `reasoningEffort: 'none'`, and GPT-6 Astra cannot call tools through the SDK. The effort set is always sent unchanged.
- **Golden traces, regression detection and run comparison match events by what they mean.** `validateAgainstGoldenTrace`, `detectRegressions`, `replayAndValidate`, `compareRuns` and the regression suites paired events by id, which is new in every run: a run doing exactly the same thing again had every event "removed" and "added" and never passed (an identical re-run failed CI with exit code 1), and `compareRuns` found every event of two runs different. Events are now paired in order in three passes — identical events, then events of the same type and subject (the tool, the operation, the answer) whose data changed, then events whose type changed for the same subject — each a longest common subsequence (in linear memory for long runs), inside the gaps the previous pass left: a call inserted before an identical one is one added call, an `action.executed` that became `action.failed` one change, an identical event found elsewhere a move. Their data is compared without ids, times, metadata, and the values the SDK writes that change between runs, removed only where the SDK writes them (the `duration` of an action, the `usage` of a model call, of a discarded answer or of a failed operation, `delayMs` of a retry, `approvalId`, `replayOf`, observation times and source events, the run id in knowledge evidence): a tool's parameters, result and input are always compared, whatever their keys. The text a model writes next to a tool call is compared in `intention.generated` only (the same call with another preamble changed every event carrying the intention), and `incident.reported` events, which depend on deliveries and throttling, are left out. Timestamps were compared absolutely with a 0 ms tolerance, and a duration 1 ms longer or shorter was a regression; with `maxDurationDiff` and `maxEventCountDiff` both set, behavioral regressions that were not critical were hidden (`no_regression`); `similarityScore` counted events with the same id (0 between two runs). See Changed for the options.
- **Regression suites run every suite, from any process.** `runRegressionTests` ran only the first suite found in the folder (directory order): it now runs every suite of the agent, oldest first. A suite recorded only the agent's id, which is new in every process, so a saved suite could not run anywhere else ("Agent <id> not found"): suites now also record the agent's name, and run with the agent of that name. A test past its `timeout` left its run going and a timer holding the process for up to 60 s, and counted neither in the CI exit code (0) nor in JUnit (a passing test case): the run is now cancelled (the result waits up to 1 s for it to record its cancellation), the timer cleared, and a timeout gives exit code 2; a `timeout` above 2 147 483 647 ms, which a Node.js timer fires at once, is refused. `stopOnFirstFailure` now stops on the first test that does not pass (an error or a timeout too, not only a regression). With `parallel`, `stopOnFirstFailure` dropped the results of tests that had run. A suite accepted any input: one without a `message` ran the agent without a message. A suite created in the process kept the `signal` and the callbacks of an input in memory, though its file cannot hold them: every test run called that `onEvent` or `onText` there, and not in another process; they are now dropped, and `RegressionTestInput` omits `onEvent`, `onText` and `onTextRestart` besides `signal`. The runs of a suite are real runs: `sdk.subscribe` listeners get their events, as they get a replay's.
- **Advanced queries work on every built-in store.** `queryEventsAdvanced`, `countEventsAdvanced` and `getEventStatistics` threw with the default file store unless given a `runId`: the file store is now read run by run. With the SQL stores, the database kept only the filter's type and ids before `not` negated the whole filter, so `{ type: 'run.started', not: true }` counted 0 instead of every other event, and `logic: 'or'` still required the type and ids; the database now narrows the events only when every condition must hold.
- **PostgreSQL: `queryEvents` and `countEvents` work.** Inherited from the SQL store, they wrote `?` placeholders (`LIMIT ?`), sent each filter value twice ("bind message supplies 2 parameters, but prepared statement requires 1"), parsed JSONB columns that `pg` had already parsed (`"[object Object]" is not valid JSON`) and returned `COUNT(*)` as a string, so `getEventsByAgent`, `getEventsByUser`, `getEventsBySession` and the advanced queries failed. `getEvents` returned `timestamp` as a string (a BIGINT).
- **`dataQuery` and `metadataQuery` of the SQL stores.** Their `field` was written into the SQL text (`data->>'${field}'`, `JSON_EXTRACT(data, '$.${field}')`): a crafted field could change the query. Paths are now checked (names of letters, digits and `_` separated by `.`, else a `ValidationError`) and bound as parameters, with the values. PostgreSQL compared `data->>'field'` with `JSON.stringify(value)`, so a string never matched, handled only `eq`, `ne` and `exists` on data, and silently ignored `metadataQuery` and the other operators (unfiltered rows came back); SQLite compared JSON text with a JSON-quoted value (strings and numbers never matched) and cast any text to a number for `gt`… Every store now gives the same results: `eq`/`ne` compare a string, number, boolean or null of the same JSON type (a missing field is `ne` anything), `gt`… numbers only, `contains` is a case-sensitive substring of a string, `exists` a value that is not null; another operator or value is refused.
- `FileEventStore.getEvents(runId, filters)` ignored `agentId`, `userId`, `sessionId`, `dataQuery` and `metadataQuery`, and read `limit: 0` as no limit: `getDecisionPatterns({ agentId })` on the default store counted the events of every agent. It now applies every filter as the other stores do, and refuses a field query that is not one.
- **`compareVersions` can succeed.** It looked for two versions among the runs of one agent id, which has a single version, and threw with the file store. It now compares the runs of every governed agent with the agent's name (the name given, or the name of the agent of this SDK whose id is given) for two declared `version`s or two `configHash`es, on every store; replays are left out; a version with no run throws a `ValidationError` listing the recorded ones ("no version" for runs that record none), and so do two equal versions, or two that select the same runs (every agent is `1.0.0` by default, so `1.0.0` and a config hash can).
- **`evaluateAssertions(runId)` evaluates the run's own assertions.** It evaluated every agent's assertions on every run: it now evaluates the assertions for every run plus those of the run's agent (by id, or by name from another process). An unknown id in `assertionIds` was skipped (a typo gave a report where everything passed) and a run without events was evaluated as empty: both throw. A `custom` assertion stopped working once the assertions were listed, reloaded from a file that could not hold its function: custom assertions are kept by the SDK instance that defined them and never written to `assertionsDir`. Migration: the files earlier versions wrote for custom assertions have no function and no agent: they load as assertions for every run and give `error`; delete them from `assertionsDir`. `defineAssertion` refuses a condition that could never be evaluated with a `ValidationError` (a missing `eventType`, `afterEventType` or `customEvaluator`, an `event_count` without `count`, `minCount` or `maxCount`, an empty `eventTypes`…); it was accepted and every evaluation was an `error`, or an unbounded count always passed.
- **JUnit reports are valid XML, with errors as errors.** Control characters in a message (the ANSI escapes of a colored log, a NUL) and unpaired surrogates were written as they were, which XML 1.0 forbids: CI servers could not read the report. They are now removed. Tests that could not run (an error, a timeout) were counted in `errors` but written as `<failure>`: they are `<error>` elements now.
- **The `cost` metric of `analyzeImpact` is a cost.** It was the number of tool calls times 0.01, labelled "tokens"; it is now the USD of each run's priced model calls, as `getRunCost` computes it with `SDKConfig.pricing`. An empty list of runs throws a `ValidationError` instead of giving `Infinity` minimums.
- **Security: ids can no longer name files outside their folder.** A run id given to the file event store (`getEvents`, `append`, a replay) and the ids of golden traces, regression suites, impact analyses and assertions were joined to a path as they were: `../x` read, wrote or deleted files next to those folders (`deleteGoldenTrace('../victim')` deleted `victim.json`). An id may now only use letters, digits, `.`, `_` and `-`, and not start with a dot; the event store refuses others with a `ValidationError` (`checkRunId`, also used by `sdk.decisions` before the paid call), and the managers find nothing to read or delete. `getRunIds` skips a file whose name is not such an id (a copy, or a run recorded by an older version under an id with a space or `:`); rename those files to keep reading them.
- **SQL event stores wait for their schema.** `SQLEventStore` (and `PostgreSQLEventStore`, `SQLiteEventStore`) created its table without waiting: on a new database the first write could run before the table existed, and a database unreachable at start-up left an unhandled rejection that stops a Node process. Every query now waits for the schema; if its creation fails (database not reachable yet), the operations waiting for it report the error and the next operation tries again. `close()` lets a schema creation in progress finish, for PostgreSQL too. With a schema-qualified table on SQLite (`app.events` in an attached database), the indexes are now created (`app.idx_events_…` on `events`); they never were.
- **`maxCost` budgets apply.** `BudgetLimit.maxCost` was never read: a cost cap never refused anything. Each model call of a governed agent now adds its cost (from `SDKConfig.pricing`, on the model that answered, else the one requested) to the agent's budgets per period and to limits that name no agent, which therefore sum every governed agent. A `budgetLimit` with `maxCost` refuses tool calls once the spend is over it; a model call itself is never refused. With `toolName`, that tool is refused on its agent's (or everyone's) spend, since model calls are not attributable to one tool. When a call's cost is unknown (a model without a price, or no input/output token counts), the cap cannot be checked and tool calls are refused, with that reason. A `maxCost` that is not a finite number ≥ 0 (a string such as `'0.5'` read from a config file, `NaN`, a negative amount, `Infinity`, `null`) is refused when the policy is applied (see *Policies are checked when they are applied*). Cognitive agents' and `sdk.decisions` calls are counted too (see *Cognitive agents' and `sdk.decisions` calls count in budgets per period*). `sdk.getBudgetUsage` reports `costUsd`, `unpricedCalls` and `unmeteredCalls`.
- **Run costs no longer report $0 for calls whose cost is unknown.** `sdk.getRunCost` (and `computeRunCost`) skipped a model call recorded without `usage` or without a model name, and counted one with a total alone as 0 tokens; a cognitive thought or a Jev decision whose vendor reported no token counts was recorded as 0 tokens: a run could report `totalUsd: 0` and `complete: true` for calls it could not price. Such a call is now counted as unmetered, as budgets count it: the report has `unmeteredCalls` and `unmeteredModels`, a line its `unmeteredCalls`, `unpricedCalls` counts the calls of models without a price, `complete` is `false` whenever the cost of a call is unknown, and `totalUsd` only adds up the known costs; a line none of whose calls reported token counts has no `costUsd`. A call that recorded no model name is listed as `(unknown)`, a name no model id uses, and never priced. The final answer of a cognitive run (`intention.generated` with `source: 'cognition'`) is not a model call and is not counted.
- **Billed calls whose step fails are counted.** A model call the vendor answered is now recorded and counted — in the run's events, in `getRunCost` and, for governed agents, in budgets per period and the run's `maxTokens` — even when the SDK then fails the step on its answer, in these cases:
  - a governed agent's tool call whose arguments are not valid JSON was in the run's events but not in the agent's budgets, so a `maxCost` or `maxTokens` budget missed it;
  - an OpenAI answer without any choice, billed with its usage, was dropped when it failed the call or a fallback took over (also when a custom `retryOn` retried it): it is recorded as a `provider.answer_discarded` event and counted, in governed runs and in cognitive thoughts alike, priced at the model that gave it (not at the model that answered after it), and a replay counts its tokens in the run's progress, as the original run did;
  - a cognitive operation cut short by `stop()` or the run's timeout lost the attempts already billed (an invalid reply whose repair was interrupted): they are recorded in `cognition.operation_failed` with their `usage`; a hypothesis comparison interrupted during its second request keeps the first one's `decision.evaluated`;
  - a typed decision whose answer does not match its questions (a choice that is not one of the options, a missing or mistyped answer) was billed but never recorded: `sdk.decisions` records it as `decision.evaluated` with the `error` and empty `answers` before throwing, and the typed-decision controller and hypothesis assessor record it before falling back; a body that is not a valid answer is recorded when it reports its usage.

  Retries and failovers after an HTTP error, a timeout or a lost connection are not counted: no answer, no usage. An answer that arrives just as the run is cancelled is still dropped by the OpenAI and Anthropic providers without its usage. When the event store cannot record a discarded or rejected answer, the provider's or the decision client's error is still the one thrown.
- **Budgets and run costs count each model call alike.** Two differences remained between budgets per period and `getRunCost`:
  - an answer a provider discarded carried only the model that answered, and budgets priced it on that name alone (no price for `vendor-1-2025` under a `vendor-1` key: a cost unknown, which a `maxCost` limit refuses), while `getRunCost` borrowed the requested model of another call of the same model. A discarded answer now carries the model its request asked for (`DiscardedAnswer.requestedModel`, recorded in `provider.answer_discarded`), and is priced on it in both. `getRunCost` has a line per model, model asked for and source, and never lends one call the requested model of another;
  - a usage with a total alone counted as tokens in budgets and as 0 tokens in `getRunCost`, and a total that disagreed with the input and output tokens was counted in budgets and in a run's `maxTokens`, the split in `getRunCost`; a usage with a malformed field (a `null` total, a negative count) was dropped whole by `getRunCost` and read field by field by budgets, where a `NaN` count made the budget's tokens and cost `NaN`. All of them now read each count on its own (a value that is not a number of 0 or more is missing) and count a call alike: a call that reported both its input and output tokens is metered, with these tokens; any other call has an unknown cost, and its tokens are the largest of its total and the sides it reported. `getRunCost` reports those in a line's `unmeteredTokens`, and a cognitive thought's usage keeps them (`unmeteredTokens`). **Behaviour change:** a call that reported one side only (input tokens alone) was priced as if complete, with 0 on the other side, and counted fewer tokens than its total: its cost is now unknown (`complete: false`, and a `maxCost` limit refuses), and its tokens are never fewer than its total. The built-in OpenAI and Anthropic providers always report both sides. The Jev client reads its usage field by field too: a `null` count no longer rejects the answer ("Unexpected response shape"), and a usage without the input tokens Jev bills has an unknown cost (output tokens alone gave a usage priced at $0 as if complete); output tokens it leaves out still count 0, as Jev does not bill them.
- **A cognitive thought a fallback answered is priced on what was asked of it.** `LLMThoughtGenerator` recorded its own model as `requestedModel` even when a `FallbackProvider` sent a fallback of another vendor its own default model instead: the fallback's tokens were priced at the primary model's price, in `getRunCost` and in budgets. It now records what the chain asked of the provider that answered (`FallbackResult.requestedModel`), and nothing when it named no model. When a repair is answered by another model than the attempt before it (the primary failed on the repair, a fallback answered), that earlier attempt is no longer added to the thought's usage, priced on the last answer's names: it is recorded as a discarded answer (`provider.answer_discarded`), priced on its own. A discarded OpenAI answer names the model its request asked for only when the request named one, as the answers that are used do (it named the provider's default). Golden traces and regression suites recorded before this version see the new `requestedModel` of `provider.answer_discarded` events as a change, and the discarded answer of such a repair as an added event.
- **`PolicyEngine.recordModelUsage` checks `calls` again**: a count that is not a whole number above 0 (`NaN`, `0`, a fraction, `Infinity`) counts 1 call, as it did before the check was dropped.
- **OpenAI's own API is not asked twice for a streamed request it refuses.** Every 400 or 422 to a streamed request asking for its usage was sent again without `stream_options`, in case the server refused the field: on OpenAI's own API, which takes it, a request refused for another reason (a context too long) was sent twice. It is now sent again only to other servers.
- **A stream that breaks off after the whole answer gives that answer.** An OpenAI stream cut, or stalled, after its finish reason — and its usage, when it was asked for — but before `[DONE]`, and an Anthropic stream cut or stalled after `message_stop`, failed as a connection failure: the call was tried again and the usage of the answer already received was lost. That answer is now used, unless a tool call's arguments do not parse (a server that sent the finish reason before their last piece): the call is then tried again, as before. An OpenAI stream that gave only its usage before it broke off reports it as a discarded answer (`provider.answer_discarded`) before the call fails.
- **Budget and timeout policies now apply.** They were checked with step 0, 0 tokens and a start time of "now", so `maxSteps`, `maxTokens` and `maxDuration` never denied a call, and token budgets per period counted nothing. A governed agent now passes its run's step, tokens and start time with each tool call, and records the tokens of each model call for the agent's token budgets (limits that name no agent count them too). A refusal gives the policy's own reason ("Max steps (10) exceeded"), and a replay applies these limits as the original run did, so a call they refused is refused again.
- **Failover between vendors.** A fallback received the agent's model, so failing over from OpenAI to Anthropic sent `gpt-4` to Anthropic, which refuses it. A fallback now gets the requested model only if it serves it, and its own default model otherwise. `intention.generated` names the provider that answered and the model actually requested; when every provider fails, the error names each attempt with its own message.
- **The primary API key is never sent to another vendor.** A fallback without a key of its own got the SDK-wide `apiKey` (an OpenAI key sent to Anthropic, or to its `baseURL`). It now takes its key, model and address from its `config`; a fallback of another vendor then from its vendor's `providerConfig`, and one of the primary's vendor from nothing but the SDK-wide `apiKey` (it never inherits the primary's `providerConfig`, whose address may be the failing gateway).
- The Anthropic provider reports the model the API answered with, not the requested one, so costs are priced on the model that served the call.
- **Cancellation reaches the vendor.** An already cancelled call is no longer sent (nor billed), and an aborted call cuts the HTTP request instead of waiting for the full answer; a fallback chain stops at once. The reasoning engine also honours `ReasoningContext.abortSignal`.
- Provider settings follow the documented priority, field by field: run provider-specific > run default > agent provider-specific > agent default (an agent's provider-specific value used to beat a run default).
- **Recent Claude models work.** Claude Opus 4.7 and later, Sonnet 5 and the Fable and Mythos models refuse `temperature` with a 400, which the SDK always sent: it is no longer sent to them. Without a `maxTokens` setting, Claude 4 and later get 16 000 output tokens (thinking, on by default for Opus 5, Sonnet 5 and Fable, counts in it), Opus 4 and 4.1 8 192, Claude 3 4 096. Model ids behind a platform prefix or suffix (`anthropic.claude-…`, `…@date`) follow the same rules.
- `FileEventStore.destroy()` waits for the creation of the store's folder: a caller deleting the folder right after could race with it.
- The file event store could write a run before its folder existed (the folder is created in the background at start-up); writes now wait for it. Seen as a rare `ENOENT` under load.
- Budget limits that name only an agent (or only a tool) never counted tool calls, so they never stopped anything: calls are now counted for every scope a limit can name (agent and tool, agent, tool, all).
- Tool parameter schemas sent to LLMs and MCP clients kept only property types: enum values, descriptions, nested objects and array items were lost, so models invented arguments (seen with a real model inventing a metric name). They are now converted with `zod-to-json-schema` (new dependency).
- `seek_information` no longer spends two attempts on a question no available tool can answer: the unknown is dropped at once with the reason, so the other open questions get their turn. A step that brings no observation is recorded as failed.
- The minimum zod version is 3.25.28 (required by `zod-to-json-schema`).
- The model sees the experiments already run and their results, and is asked for untested, discriminating tests: with a real model, runs stopped repeating the same experiment.
- Jev reached through Vercel AI Gateway (`typesafe-ai/jev`) is priced by default; the typed decisions guide and the cognitive example show how to use an AI Gateway key.
- A 429 meaning the account is out of credit or quota (`insufficient_quota`, `credit_balance_exhausted`, billing limits) is no longer retried: it failed only after useless waits. Found with a real OpenAI key.

- **Studies.** `sdk.createStudy(config)` creates a researcher that understands an object, then proposes how to redesign it with the knowledge and techniques of today, following a method of seven passages (`observe`, `decompose`, `historicalChoices`, `changes`, `cross`, `design`, `confront`) that form a loop: a passage may reopen an earlier one (`limits.maxLoops`, 1 by default). It builds, runs and measures nothing. It gives a verdict on each of your `leads` (examples to verify, not truths) and looks for other tools beyond them, lists the best current realisations, deconstructs breakthroughs by assembly (`analogues`, such as Bitcoin), and designs at least two architectures aiming at a **new capability** — a change of principle that makes possible something difficult today, not only faster (`capability`, or candidates proposed by the study) — each with its components, assembly, mechanism and coverage of the object's whole chain, capabilities ranked before improvements; then the three states of each piece, the experiments that would decide, and a mechanism card per main mechanism, whose fields 10 and 11 `study.recordResult(cardId, { result, error?, conclusion? })` fills once you ran the experiment.
  - **Research through your sources**: `sources` names SDK tools, typically the tools of an MCP search server imported with `connectMcpServer`; every search runs through `executeTool` (allowlist, policies, budgets, approvals, retries, traces) under the study's `id`. Results are numbered once per study (`S1`…), each field on one line; a text answer written as `Title:` / `Description:` / `URL:` blocks gives one result per block, the prose under a block going into its excerpt, and an answer such as "No results found" is not a result. Every text from outside the study (the results, the descriptions of the sources, the rejected items a redo is told about) reaches the model as a labelled JSON block between `<<<UNTRUSTED-DATA-<id>` and `UNTRUSTED-DATA-<id>>>` lines, with a random id per prompt. The SDK builds in no Web search.
  - **Claim statuses checked in code**: `established` only when a claim cites a result listed in the prompt that wrote it, else a `hypothesis` with the reason (and the ids its prompt did not list, `unlistedSources`); a `novelty` stays to verify until its prior art has been searched and assessed from the results of its own searches, and becomes a `hypothesis` when the work already exists; the assembly of every capability architecture is searched for prior art as a combination, whatever its status, and statuses are only ever lowered: a capability whose assembly already exists keeps its kind, says so (`priorArtReason`: `assemblyExists`, notice `capabilitiesExist`) and is ranked after the other capabilities, before the improvements, and one whose prior art could not be checked is marked `toVerify` with why (notice `capabilitiesToVerify`); a component of an assembly is never a novelty, and every component and assembly link names the records of the investigation it comes from (`from`, or `untraced`, notice `untracedAssembly`). Without sources nothing is established, and the report says so first. Every reason is a `StudyReason` (`code`, `params`, English `message`) that the dossier renders in the study's language.
  - **Staying on the objective**: the charter (object, question, objective, needs, leads and breakthroughs numbered, scope, capability) is frozen and hashed (SHA-256, recorded in `study.started`); every prompt is rebuilt from the charter, the accepted amendments, the task and compact records of the items the guardian judged — never a conversation — and its reminder restates the capability aim and ends with the objective; every item must say what it serves (`servesObjective`) or is refused; after each passage a guardian call judges each item — for the design, with its mechanism, components and assembly — removes those off the objective into a drift log, and has the passage redone once past `driftThreshold` (a third by default), keeping the better attempt (a redo that cannot be judged leaves the first one standing, and a discarded redo is reported). The guardian fails closed: an item without a valid verdict stays `unchecked`, out of every later prompt, a guardian that judges none fails the run, and when a repair cannot be used, or the provider fails on it, the valid verdicts of the first reply still count. Items judged late reach the passages that ran without them: those run again as a loop does, or stay outdated (notice `passagesOutdated`) until a later run. `study.amend(text, { signal?, timeoutMs? })` is classified against the charter alone, one amendment at a time, and accepts only an instruction that refines the objective (two amendments that contradict each other can both be accepted) (at most 10, of at most 500 characters: `MAX_AMENDMENTS`, `MAX_AMENDMENT_LENGTH`); a new objective is a new study.
  - `study.run({ signal?, onEvent?, restart? })` returns `{ runId, status, stoppedBy?, error?, report, markdown }`: a structured `StudyReport` and a dossier in the study's `language`, with its words in 11 languages (`renderStudyMarkdown`, `studyLabels`). Limits per run (`DEFAULT_STUDY_LIMITS`): `maxModelCalls` 60, `maxSearches` 20, `maxLoops` 1, `timeoutMs` 20 minutes, `maxResultsPerSearch` 5. Twelve new event types (`study.started`, `study.passage_started`, `study.passage_completed`, `study.search`, `study.model_called`, `study.drift_rejected`, `study.capability_demoted`, `study.amendment_accepted`, `study.amendment_refused`, `study.result_recorded`, `study.completed`, `study.failed`); `getRunCost` and budgets per period count `study.model_called` under the study's `id`; comparisons pair study events by passage; MCP progress notifications describe a study's run by passage, then `report ready` or `partial report ready`. Example `examples/study.ts` (`npm run example:study`), which gives the MCP search server only the variables named in `SEARCH_ENV` and exits with the code 1 when the run did not complete.
  - Good to know: `maxSearches` does not end a run: once spent, the study goes on without searching and says so (notice `searchesSkipped`), claims that needed a source stay hypotheses and novelties stay to verify. `maxModelCalls`, `timeoutMs` and budget or timeout policies (checked before each step: a passage, a redo, a reopening, an amendment) end it with the status `stopped`, `study.failed` and `run.failed`; a cancelled run ends with `run.cancelled`. A run that stops keeps what it did, and the next `run()` resumes: the guardian first judges what was left unjudged, a passage stopped after its first attempt takes the redo it was due, then the passages not complete run; `restart: true` starts over, keeping only the charter and the amendments. An amendment is classified in a run of its own (`mode: 'study-amendment'`), where its cost is counted; one that times out, is cancelled, is refused by a policy or cannot be classified is refused (`unclassified`). `recordResult()` is asynchronous and records `study.result_recorded` in the run that wrote the card. `stats.runs` and `stats.modelCalls` count the runs of `run()` and the calls the vendor answered; amendments are counted apart (`stats.amendments`). A study's state lives in its `Study` object: the SDK does not rebuild a study from its events.

- **OpenAI options** in `providerConfig.openai`, in the `config` of an OpenAI fallback (a fallback of another vendor takes each option its `config` does not set from `providerConfig.openai`) and in the options of `OpenAIProvider`: `reasoningModels` (`true` or `false` for every model, or the list of names that are reasoning models, for names the SDK cannot recognize such as Azure deployments or gateway aliases), `reasoningEffort` (`none`, `minimal`, `low`, `medium`, `high`, `xhigh` or `max`, sent as given to reasoning models only; the API refuses the values a model does not accept) and `nativeToolMessages` (`false` for an OpenAI-compatible server that does not accept assistant `tool_calls` and `tool` messages in the conversation: earlier tool calls and results then go as plain text, while tools are still offered and the tool calls of replies still read; `false` on the primary or on any fallback applies to the whole chain). `createSDK` and `OpenAIProvider` refuse a value of the wrong type with a `ValidationError` naming the option (`providerConfig.openai.reasoningModels`, `fallbackProviders[1].config.reasoningEffort`…): a string given as `reasoningModels` would have matched every model name it contains. - **Live events.** A run's events reach your code while it runs, once the event store has accepted them: `agent.run({ onEvent })`, `cognitiveAgent.think({ onEvent })`, `sdk.replay(runId, modifications, { onEvent })`, and `sdk.executeTool(name, params, { onEvent })`, which also gets the events of the agent run a `governedAgentTool` or `cognitiveAgentTool` starts (through the new `ToolCallContext.onEvent`; one level deep, and best effort: an agent built by hand on a store that does not deliver live events runs without it). `sdk.subscribe(listener, { runId?, agentId?, types?, maxQueued? })` watches every run (dashboards, logs) and returns the function that unsubscribes. Within a run, events arrive in the order they were recorded, even when appends overlap, and never for an append that failed; each listener gets its own copy, one event at a time (a promise it returns is awaited before its next event). The run never waits for a listener. Once it is over, `run()`, `think()`, `replay()` and `executeTool()` wait until their `onEvent` has settled on every event, unless the run was stopped or cancelled or its `signal` aborts (for a cognitive run, `limits.timeoutMs` counts the wait too): the listener is then unsubscribed and what it had not received is dropped. At most `maxQueued` events (default `DEFAULT_MAX_QUEUED_EVENTS`, 10 000) wait for a busy listener; past that, new events are dropped for it and reported once it catches up with a `LiveEventsDroppedError` saying how many. A listener that throws or rejects is reported on standard error and still gets the next events. The layer that delivers them is `ObservedEventStore` (exported, with an `onListenerError` option for errors and drops): the SDK always wraps its store in one, inside the incident monitor, so `incident.reported` events are delivered too, and uses the one you give as `eventStore`, also inside a `MonitoredEventStore` you build (whose store is now readable as `inner`); `IEventStore` has an optional `subscribe`. An `onEvent` you pass that is not a function, or that you give to an agent built by hand on a store that does not deliver live events, is refused with a `ValidationError` before anything is recorded. Guide: *Traceability & replay*, section *Live progress*.
- **MCP progress notifications.** A `tools/call` carrying a `progressToken` gets a `notifications/progress` for each event of the call, the agent run it starts included (one level deep, not coalesced: a long cognitive run can send hundreds), with a `progress` that goes up by one and a short message (`step 1: tool lookup_customer called`, `waiting for approval of delete_customer`) that holds no arguments, results or error texts, but names the tools the agent calls, those the server does not expose included. All of them are sent before the result. A client that resets its timeout on progress (TypeScript SDK: `resetTimeoutOnProgress: true`) can then wait for a call longer than its timeout; nothing is sent while a tool runs or an approval waits, so `approvalTimeoutMs` keeps its 50 s default. Deploy guide: *Progress notifications*.
- **Streamed text.** `agent.run({ message, onText })` receives the text the model writes, delta by delta, while it is generated. The OpenAI provider then calls chat completions with `stream: true`, the Anthropic provider the Messages streaming API, and both still return the complete response: text, tool calls with their ids and input, usage, and for Claude the turn with its thinking blocks (redacted ones included). The text of every model call of the run is passed on (what the model writes before calling a tool, then its answer), a blank line before the text of a call when an earlier call wrote some; tool arguments and thinking are not. A provider that cannot stream gives each call's text in one piece when the call ends. When a call fails after part of its text was passed on and is retried or passed to a fallback provider, `onTextRestart(discarded)` receives that part (blank line included), to drop: the next attempt writes the answer again, and `provider.retry` or `provider.fallback` is recorded as before. What the callbacks throw is ignored (abort `signal` to stop the run), and neither is recorded in the run, nor in a replay's input. Cognitive agents do not stream: their model calls return structured thoughts. Documented in the governed agents guide (*Streaming the answer*), the SDK API reference, the retries guide and the development guide.
  - OpenAI-compatible servers: the usage of a streamed answer (`stream_options.include_usage`) is only asked for on OpenAI's own API (`https://api.openai.com/v1` or a regional host such as `https://eu.api.openai.com/v1`, set by `baseURL` or `OPENAI_BASE_URL`), since a compatible server may refuse the field or ignore it. The new OpenAI option `includeStreamUsage` (in `providerConfig.openai`, the `config` of an OpenAI fallback, which inherits it like the other OpenAI options, and the options of `OpenAIProvider`; a value that is not a boolean is refused with a `ValidationError`) turns it on or off: set it to `true` for a cost budget on a compatible server that reports the usage, such as the Azure OpenAI v1 API. A 400 or 422 to a streamed request that carried the field, whatever its body (a FastAPI validation error, an error at the top level), is followed by the same request without it; when that one is accepted, the field is no longer sent. A streamed call without usage counts as unmetered in budgets, as a non-streamed one without usage always did, and a stream that ends with usage but no answer is reported as a discarded answer (`provider.answer_discarded`) once, as a non-streamed one is. When OpenAI refuses to stream a model (a 400 about `stream`, such as "Your organization must be verified to stream this model"), the call is made again without streaming, its text given in one piece, and that model is no longer streamed.
  - A stream that sends nothing for the client's timeout (10 minutes by default) is cut: the vendor clients stop their timeout once the answer starts. New `timeout` option, in milliseconds, of each vendor's `providerConfig` entry, of a fallback's `config` (a fallback of another vendor takes its vendor's entry, as for `baseURL`) and of `OpenAIProvider` and `AnthropicProvider` (`VendorClientOptions`), passed to the vendor client: a value that is not a number of milliseconds above 0 that a timer can wait (at most 2 147 483 647) is refused with a `ValidationError` naming it. It fails as a connection failure, retried or failed over, like a stream whose connection drops or that ends before its answer is complete.
  - For your own provider: `LLMRequest.onTextDelta(delta)` asks for the text as it is written (the pieces joined make the response's `content`; a provider that cannot stream ignores it), and `LLMRequest.onTextRestart()` voids the text streamed so far. `RetryingLLMProvider` and `FallbackProvider` pass both on and call `onTextRestart` between attempts that had streamed text; what a failed attempt still sends after it failed is dropped.

- **Agents keep their identity across processes.** The lifecycle events of a governed agent's runs record its `agentName` and `configHash` besides `agentId` and `agentVersion` (`EventMetadata`); `AgentImpl.version` and `AgentImpl.configHash` expose them. - **An MCP server for anything, in one line.** New tool sources in the core package, usable by agents and by MCP servers alike:
  - `openApiTools({ spec })` turns the operations of an OpenAPI 3 description (URL, file or parsed object) into tools: local `$ref`s resolved with a cycle guard and an expansion budget per operation and per spec, one flat JSON Schema per operation (path, query and header parameters, JSON body; bounded in size; parameters that would share an argument name are refused), arguments checked by the tool's schema before policies and approvals, base URL from the option or `servers[0]`, `headers` for authentication that the model never sees and cannot override (with them, `baseUrl` is required unless the spec comes from the API's own origin, and `http:` — for the API and for downloading the spec — only on loopback), path values that cannot contain `/`, `\` or dot segments even percent-encoded (malformed escapes included), injectable `fetch`, timeout, responses cut at `maxResponseBytes`, redirects refused (also when a custom `fetch` followed one), non-2xx statuses as tool errors. **Read-only by default**: only `GET` operations, unless others are listed in `include` — they are then `riskLevel: 'high'` and `requiresApproval: true` unless `metadata` sets a field explicitly. `retry` applies to read-only operations, on 5xx, 429, timeouts and network failures only.   - `test_prediction` runs your `OutcomeEvaluator` (no LLM call) and records a `cognition.evaluated` event;
  - `revise` turns a refuted or contradicted hypothesis into a variant with `parentId`, scope and a required `difference`.
- **Observations with provenance**: `think({ observations })`, tool results and test results become observations (`O1…`) with source, event id, time, context, fingerprint and origin group; repeated evidence is marked as a duplicate and adds no weight; facts cite the observations they come from, are not added twice, and can be retracted or superseded.
- **Hypotheses** state their `kind` (proposal, rule, explanation), inference, premises and scope; **predictions** (`P1…`) carry an expected result, a falsifier and test parameters, are recorded before they are tested and tested once. A refuted prediction rejects its hypothesis and is logged as a resolved `refuted_prediction` contradiction; an inconclusive or failed test, or a refutation that reports no observation, never rejects anything.
- **Evidence kept apart from preferences**: `support` (evidence) and `preferenceFit` (thinker fit, proposals only) are separate scores; only proposals are ranked with preferences (`limits.preferenceWeight`); the state's confidence is the evidence support of the best-ranked hypothesis.
- **Stale assessments**: an `evidenceRevision` counter makes earlier assessments stale when the evidence changes; a comparison must reassess every hypothesis in play (the LLM is asked to repair an incomplete one), and one that fails or skips a hypothesis does not count.
- **Conclusion guard**: `decide` is offered only when a hypothesis is critiqued, freshly assessed, free of unresolved contradictions in its scope, has no untested prediction while tests are possible, and reaches `decisionThreshold`. A decision that is not ready, or selects no hypothesis, is deferred while the budget lasts; a forced decision becomes `provisional` with `missing`, or an `abstain` (confidence 0) — also when the model cannot produce a decision at all. Decision confidence is capped by evidence support.
- Contradictions have a category and are resolved once, only with cited observations or facts; the resolution and its action are kept. Engine-found contradictions are not duplicated.
- Thinker feedback accepts `agreement` (share the thinker agreed with) and `wrongAbout` (where the reasoning went wrong); both are kept with corrections and `agreement` is exported with the controller dataset.
- Options `evaluator`, `generator` and a custom `HypothesisAssessor` for `assessment`; limits `maxPredictionTests` and `preferenceWeight`.
- Building blocks exported: `assembleThought`, `admitProposal`, `settleDecision`, `assessReadiness`, `rankHypotheses`, `PredictionTester`, observation builders and their types.
- Documentation: *Evidence & verification* guide, new evidence-loop illustration, updated loop and architecture illustrations, `examples/rule-discovery.ts`.

### Changed
- Every thought enters the state through `assembleThought`: fields are restricted per operation, engine-only fields (observations, test results, failures, decision status) are stripped from proposals, and an invalid thought from a custom component is recorded as a failed operation instead of stopping the run. Components receive a copy of the state.
- A step that changed nothing it was meant to change (no new hypothesis, nothing newly simulated or critiqued, no comparison recorded), an incomplete comparison and a deferred decision count as failed attempts of their operation; `compare_observations`, `hypothesize`, `simulate`, `revise`, `critique`, `compare` and `decide` are no longer offered after two failed attempts in a row, until another step brings new evidence (a step that succeeded, or a tool or test result recorded by the engine). Deferrals and steps without effect are recorded as failed (`cognition.thought.failed`, `cognition.operation_failed`) but do not count toward `maxConsecutiveFailures`, which counts failures of the model or its tools (an incomplete comparison after repair included).
- A repeated observation counts as the same evidence as its original (facts and test results reference the original), and the same model contradiction is not recorded twice.
- Proposals that restate an existing hypothesis (rejected or still in play) or a variant without `difference` are removed before the `maxHypotheses` cap, so they cannot take a valid proposal's place; a known fact read again gains the new source instead of being duplicated.
- `TypedHypothesisAssessor` asks evidence questions without the thinker's profile and fit questions in a second request, proposals only (the `evidenceWeight` option is removed); a missing evidence answer makes it fall back to the LLM comparison.
- `cognition.started` records `schemaVersion: 2`, initial observations and commit rules; runs without a version are rebuilt with their original rules (decision on a rejected hypothesis kept without its reference, patch confidence used, no evidence rules).
- `ActionEngine.executeIntention` returns the `tool.called` and `action.executed` events it recorded (the `events` field used to be empty).
- Public types gained required fields: `CognitiveLimits` (`maxPredictionTests`, `preferenceWeight`), `MentalState` (`schemaVersion`, `observations`, `comparisons`, `predictions`, `evidenceRevision`, `observationsCompared`, `commitRules`), `Hypothesis` (`kind`, `premiseRefs`, `evidenceRefs`, `counterEvidenceRefs`), `Fact` (`observationRefs`, `status`) and profile corrections (`wrongAbout`). `ThoughtRequest.observation` is a `ToolObservation` with an `observationId`. The patch `confidence` is only used by legacy runs, and `ALLOWED_FIELDS` no longer lists it.
- `describeMentalState` omits empty collections and adds readiness and ranking, so the `state` of exported controller datasets changes shape, for older runs too.
- `ReasoningFeedback` is the schema's input type (`wrongAbout` optional) and `refineProfile` validates it; `thoughtPatchSchema` and patch types live in `thought-patch.ts`, `describeMentalState` in `mental-state-view.ts` (both still exported from the package entry).

### Changed
- `defineTool` infers the handler parameters from the Zod schema; typed Choice answers are typed with the offered options.
- Costs include failed thought attempts and model calls per repair, and prices are looked up by the returned model id and by the requested model name.
- The run status is the last lifecycle event, so events appended after the end of a run do not reopen it.
- `FileEventStore` serializes flushes per run, takes the buffer before writing and writes atomically (temporary file + rename): overlapping flushes no longer duplicate or drop events. `getRunIds()` flushes buffered events first; `destroy()` returns a promise that resolves after the final flush. - All documentation, planning artifacts and code comments are in English.

### Fixed
- Policy engine: built-in rules (`maxSteps`, `maxTokens`, `budgetLimit`, `maxDuration`, `allowedTools`) were read as missing fields by the generic condition evaluator and never applied — budget, timeout and allowlist policies now deny as documented.
- Regression detector: an event that became a failure (e.g. `action.executed` → `action.failed`) is now a critical regression.
- Trace validator: with `compareStructureOnly`, value differences are reported and give a `partial` status instead of a silent `pass`.
- Golden trace YAML export always quotes strings, so values like `true`, `null` or `123` keep their type.
- The package-level `defineTool` builds a tool without registering it in a hidden module-wide SDK (which also opened an event store on `./events`); the SDK registers it when an agent uses it.
- Approval workflow tests now drive a real agent run through an injected LLM provider instead of calling the OpenAI API with a fake key.
- Lint: 177 Biome errors in older modules fixed (`noStaticOnlyClass` turned off: the static utility classes are part of the tested API); sources formatted; CI uses a valid `npm run format:check`.
