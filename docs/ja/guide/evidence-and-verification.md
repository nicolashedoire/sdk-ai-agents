# 証拠と検証

認知エージェントは、正当化できることを信じ、予測したことを検証し、現実の世界と食い違ったら自分の規則を変えるべきです。そのため認知ループは、**すべての証拠がどこから来たか** を追跡し、**証拠と選好を切り離し**、予測を **実際のテスト** と突き合わせ、コードで書かれた準備完了チェックを通過した回答だけを **確定** します。

::: tip やさしく言うと
慎重な調査員を思い浮かべてください。調査員は **それぞれの手がかりがどこから来たか** を記録し、同じうわさを二度数えることはしません。いくつかの事例から **規則** を導き、その規則が正しければ **何が見えるはずか**、そして **何が見えれば誤りだと証明されるか** を前もって述べます。それから、自分の意見ではなく実際の測定で確かめます。確認に失敗しても、ごまかしたりはしません。**規則を修正** し、何が変わったかを述べます。そして、それが持ちこたえるときにだけ **確かな回答** を出します。そうでなければ、「まだ確かではありません。足りないのはこれです」、あるいは「結論を出せません」と言います。以下で使う用語はすべて [用語をやさしく解説](./glossary#evidence-and-conclusions) で説明しています。
:::

## 観測したものを渡す {#give-it-what-you-observed}

すでに手元にある測定値、事例、文書を、問題と一緒に渡してください。それぞれが、推論の中で引用できる ID（`O1`、`O2`…）の付いた **観測** になります。

```ts
const result = await agent.think({
  problem: 'Does the rolling time on our plane depend on the ball?',
  observations: [
    {
      content: { material: 'steel', massKg: 0.1, seconds: 1.07 },
      summary: 'Steel ball, 100 g: 1.07 s',
      originGroup: 'bench',
    },
    {
      content: { material: 'steel', massKg: 0.4, seconds: 1.07 },
      summary: 'Steel ball, 400 g: 1.07 s',
      originGroup: 'bench',
    },
  ],
});
```

ツールの結果やテストの結果も観測になります。その出所はエンジンが書き込み、モデルが書くことはありません。

| フィールド | 意味 |
| --- | --- |
| `sourceKind` | `input`（問題と一緒に渡されたもの）、`tool`（ガバナンス付きツールの呼び出し）、`evaluation`（予測のテスト）のいずれか |
| `source`、`sourceEventId` | ツールまたは評価器と、完全なペイロードを保持するイベント（`action.executed`、`cognition.evaluated`） |
| `observedAt`、`context` | いつ、どのような状況で観測されたか |
| `summary` | モデルに示される、長さに上限のあるテキスト |
| `fingerprint` | 内容全体のハッシュ |
| `originGroup` | 出所が同じ観測は、独立した裏付けでは **ありません** |
| `duplicateOf` | 同じ出所からの同じ内容がすでに観測されていたときに設定される |

事実は、読み取り元の観測を引用します（`observationRefs`）。ツールの結果から抽出された事実は自動的にその結果と結び付けられ、すでに知られている事実が二重に追加されることはありません。その場合は、新しい情報源が裏付けとしてその事実に追加されます。モデルは、X を主張する情報源を、X の証明としてではなく「その情報源は X と主張している」と読むよう指示されています。同じ証拠を繰り返しても重みが増えないことは、コードが保証します。重複は証拠の変化として数えられず、以前の観測を繰り返す事実やテストは、元の観測を指します。

## 観測を比較する {#compare-observations}

`compare_observations` は、観測（と事実）を互いに関連付けます。比較可能な観測（問題と一緒に渡されたもの、またはツールが返したもので、重複とテスト結果は除く）が 2 つ以上あり、前回の比較以降に新しい観測が届いているときに提示されます。

| 関係 | 意味 | コードが行うこと |
| --- | --- | --- |
| `similarity` | ある側面で同じ値や振る舞いを示す | 記録する。類似は原因ではない |
| `difference` | 状況の違いで説明される相違 | 記録する |
| `evolution` | 時間とともに起きた変化 | 記録する |
| `incompatibility` | 両方が同時に成り立つことはない | 矛盾を登録する（出所をまたぐ場合は `source_disagreement`）。一度だけ |
| `counterexample` | 仮説を崩す事例 | その仮説の反証として保持し、矛盾を登録する。一度だけ |

## 規則、説明、提案 {#rules-explanations-and-proposals}

仮説は、それがどんな種類の主張なのか、どのように推論されたのか、何にもとづいているのかを述べます。

```json
{
  "statement": "Rolling time on this plane does not depend on the ball",
  "kind": "rule",
  "inference": "induction",
  "premiseRefs": ["O1", "O2"],
  "scope": "balls on this plane"
}
```

`kind` は `proposal`（行うべき行動や選択。デフォルト）、`rule`（規則性）、`explanation`（原因）のいずれかです。何が真であるか、真であったかについての言明は、決して提案ではありません。モデルにもそう伝えられています。[結論ガード](#the-conclusion-guard) は、思考者の選好が選択を後押しすることは認めても、主張を後押しすることは認めないからです。`inference` は `induction`、`abduction`、`deduction` のいずれかです。このラベルが主張を真にすることはありません。

## 予測と結果評価器 {#predictions-and-the-outcome-evaluator}

`simulate` は、外れる可能性のある **予測** を演繹します。何が観測されるはずか（`expected`）、どの観測が仮説の誤りを証明するか（`falsifier`）、どの状況（`context`）でか、そして評価器が必要とする構造化された `test` パラメーターです。予測はテストされる **前に** 記録され、テストは一度だけ行われます。モデルは、すでに行われた実験とその結果（状態ビューの `experiments`）を見て、同じ実験を繰り返さず、検討中の仮説同士で予測が食い違うテストを選ぶよう求められます。

`OutcomeEvaluator` は、予測を現実の世界（シミュレーター、測定、テストスイート、クエリ）と突き合わせます。

```ts
import type { OutcomeEvaluator } from '@sdk-ai-agents/core';

const bench: OutcomeEvaluator = {
  id: 'inclined-plane-bench',
  version: '1.0.0',
  async evaluate({ prediction }) {
    const run = await rollOnTheBench(prediction.test); // your measurement
    if (!run) return { verdict: 'inconclusive', reason: 'the bench is busy' };
    const refuted = Math.abs(run.seconds - run.expectedSeconds) / run.expectedSeconds > 0.1;
    return {
      verdict: refuted ? 'refuted' : 'confirmed',
      observed: run,
      summary: `${run.material} ball: ${run.seconds} s`,
      metrics: { seconds: run.seconds },
      ...(refuted ? { causeCandidates: ['material deforms', 'surface grip'] } : {}),
    };
  },
};

const agent = sdk.createCognitiveAgent({ name: 'physicist', model: 'gpt-4o', evaluator: bench });
```

評価器があると、`test_prediction` が利用可能になります。これは **言語モデルではなく、あなたの評価器** を呼び出し、完全なレポートを `cognition.evaluated` イベントとして記録し、観測されたものを、そのイベントを指す `evaluation` 観測として追加します。

| 判定 | 効果 |
| --- | --- |
| `confirmed` | 観測が仮説の `evidenceRefs` に追加される |
| `refuted` | 反証条件が観測された。仮説は **却下** され、観測は反証として保持され、反証は解決済みの `refuted_prediction` 矛盾として記録される |
| `inconclusive` | 記録される。何かを観測していれば、それは新しい証拠になる。それ以外は何も変わらない |

テストのたびに、`limits.maxPredictionTests` の回数を 1 つ消費します。例外を投げる評価器や、不正なレポートを返す評価器の結果は `inconclusive` になり、何が観測されたかを述べていない `refuted` のレポートも同様です。失敗した測定が何かを反証することはありません。自分の推論を判定するモデルを評価器として使わないでください。自己批判はテストの準備にはなりますが、テストの代わりにはなりません。

## 修正 {#revision}

証拠が仮説と矛盾したとき、`revise` は **バリアント** を求めます。`parentId` を持ち、より狭い `scope` か追加の変数を持ち、それがもたらす違い（`difference`）を述べた新しい仮説です。違いを述べていないバリアントは拒否されます。元の仮説は、その ID、却下の理由、反例を保持します。すでに検討された仮説を再提示することは、却下されたものかどうかにかかわらず拒否されます。斜面のテストでは、反証された規則「転がる時間はボールに依存しない」が「剛体のボールでは、転がる時間は質量に依存しない」になり、2 回目のテストでそれが確認されます。

## 証拠は選好ではない {#evidence-is-not-preference}

| スコア | 問い | 思考者プロファイルを見るのは？ |
| --- | --- | --- |
| `support` | 観測、事実、予測、批判は、それをどれだけ支持しているか？ | Jev：誰も見ない。証拠についての質問はプロファイルなしで送られる。LLM：モデルは選好を無視するよう指示される |
| `preferenceFit` | この提案は思考者にどれだけ合っているか？（提案のみ） | 見る。それがこのスコアの目的 |

コードが 2 つのスコアを混ぜることはありません。規則と説明の仮説は `support` だけで順位付けされ、提案は `(1 − w) · support + w · preferenceFit`（`w = limits.preferenceWeight`、デフォルトは 0.4）で順位付けされます。したがってプロファイルを変えると、**どの行動が選ばれるか** や、思考者が明らかに好む選択をもっともらしい程度の証拠で確定できるかどうかは変わりえます（[結論ガード](#the-conclusion-guard) を参照）。しかし Jev を使う場合、**主張がどれだけ信頼できるか** を変えることはできません。LLM が判定する場合、この分離はモデルへの指示にかかっています。状態の `confidence` は、最上位の仮説の証拠による支持度に従います。モデルが思考の中に書いた `confidence` は無視されます。

`support` はモデルによる判断であり、較正された確率ではありません。測定されるのは実績、つまりどの予測が確認され、どの予測が反証されたかです。

## 古くなった評価 {#stale-assessments}

状態は `evidenceRevision` カウンターを持っています。このカウンターは、新しい（重複でない）観測、新しい事実、事実の改訂、矛盾、反例、決着のついたテスト結果が届くたびに増えます。それ以前に行われた評価は **古くなった** ものになります。`compare` が再び提示され、評価が古くなった仮説は確定できません。比較では、検討中の **すべての** 仮説を評価し直さなければなりません。ある仮説を飛ばした比較については、モデルに修正が求められます。それでもなお仮説を飛ばした比較や、失敗した比較は、完了したとはみなされません。

## 矛盾と事実の改訂 {#contradictions-and-fact-revisions}

矛盾は `category` を持ちます。`source_disagreement`、`temporal_change`、`context_difference`、`logical_incompatibility`、`refuted_prediction` のいずれかです。矛盾は **一度だけ**、しかもその解決が、決着をつける **観測や事実を引用している** 場合にのみ解決されます（`basisRefs`。それ以外の参照は報告され、無視されます）。解決では、何を行ったかを述べられます（`retracted`、`restricted`、`replaced`、またはデフォルトの `explained`）。解決の内容は矛盾とともに保持されます。事実が削除されることはなく、理由を添えて `retracted` になるか、置き換えによって `superseded` になります。

## 結論ガード {#the-conclusion-guard}

回答を **確定** できるのは、その仮説が次の条件をすべて満たすときだけです。

- 批判を受けている。
- 証拠が最後に変わった後に評価されている。
- 未解決の矛盾に関係していない（何も名指ししていない矛盾は、すべてに関係します）。
- テストの予算が許すのに未検証のままの予測がない。
- 証拠による `support` が `limits.decisionThreshold` 以上である。あるいは **提案**（行動の選択）の場合は、明らかに思考者の選択であり（`preferenceFit` が `limits.decisionThreshold` 以上）、かつ証拠による支持度が `limits.minProposalSupport`（デフォルトは 0.35）に達している。

2 つ目の道があるのは、「この仕事を引き受けますか？」のような問いには、比べるべき証拠がほとんどないからです。人は、事実がその選択に反していない限り、つまり証拠による支持度が下限以上である限り、自分の優先事項でそれを決めます。規則と説明がこの道を通ることはありません。選好が主張を真にすることはないからです。[特定の人物のように推論する](./thinker-profiles#how-a-choice-is-ranked-and-committed) で、数値を使った例を順に説明しています。`minProposalSupport` は `decisionThreshold` を超えてはいけません。`decisionThreshold` と同じ値にすると、この道は無効になります。

`decide` は、ある仮説が通過したときにだけ提示されます。別の仮説を選んだ決定や、何も選ばなかった決定は、予算が残っている間は **先送り** されます。先送りは失敗した試行として数えられ、2 回続くと `decide` は提示されなくなります。最後のステップ、またはほかに何もできないときは、エンジンがそれでも決定を求め、次のように決着させます。

| `decision.status` | いつ | `decision.missing` |
| --- | --- | --- |
| `committed` | 準備完了チェックを通過した | `[]` |
| `provisional` | 有効な仮説がある状態で予算が尽きた | まだ確立されていないこと |
| `abstain` | 仮説が選ばれなかった、選ばれた仮説が却下されていた、またはモデルがまったく決定を出せなかった | その理由。判断保留の確信度は 0 で、回答はエンジンが書く（モデルが書いたものは `rationale` に残される） |

```ts
const { decision } = await agent.think({ problem, observations });
if (decision?.status !== 'committed') {
  console.log('Not established yet:', decision?.missing);
}
```

実行の状態は `completed` のままです。明示的な判断保留は正当な結果だからです。決定の確信度は、その仮説の証拠による支持度で頭打ちになります。

## 予算を無駄にしない {#a-budget-that-is-not-wasted}

変えるはずだったものを何も変えなかったステップ、つまり新しい仮説がない（すべての提案が拒否された）、新たにシミュレーションや批判がされたものがない、比較が記録されていないステップ。それに加えて、仮説を飛ばした比較と、先送りされた決定。これらはいずれも、そのオペレーションの失敗した試行として数えられます。`compare_observations`、`hypothesize`、`simulate`、`revise`、`critique`、`compare`、`decide` が 2 回続けて失敗すると、**別のステップが新しい証拠をもたらすまで** 提示されなくなります。新しい証拠とは、成功したステップ、またはエンジンが記録したツールやテストの結果のことで、失敗したステップが自分で書いたものは数えません。こうして、実行は同じことを繰り返さずに先へ進みます。一方、`seek_information` は未解決の問いごとに動作します。利用できるツールでは答えられない問いは（理由を添えて）直ちに断念され、失敗したツール呼び出しは各問いに与えられる 2 回の試行のうちに数えられるので、ほかの問いにも順番が回ってきます。`test_prediction` は、テストの予算によって制限されます。

`limits.maxConsecutiveFailures` が数えるのは、モデルやそのツールの失敗で、修正後もなお仮説を飛ばした比較も含まれます。先送りされた決定や、何も変えなかったステップは、失敗したステップとして記録されますが、この数には含まれません。構成要素（思考ジェネレーター、アセッサー、評価器）には状態のコピーが渡されます。構成要素が記録済みの内容を書き換えることはできず、独自の構成要素から不正な思考が返ってきた場合は、実行を止める代わりに、失敗したオペレーションとして記録されます。

## テストが仕様書 {#tests-are-your-specification}

`src/__tests__/rule-discovery.test.ts` は、台本どおりに応答するモデルと決定論的な物理ベンチを使ってループ全体（帰納、予測、反証、修正、検証、確定）を実行し、すべてのイベントをチェックします。`src/__tests__/epistemic-state.test.ts`、`epistemic-guards.test.ts`、`epistemic-liveness.test.ts` は、上記の各ルールを個別にチェックします。さらに、以前のバージョンで記録されたトレースを使って、古い実行が変わらずに再構築されることをチェックします。

## 古い実行 {#older-runs}

実行は、これらのルールのバージョン（`cognition.started` の `schemaVersion: 2`）を記録します。それ以前に記録された実行にはバージョンがありません。`getMentalState` はそれらを元のルールで再構築し、新しいコレクションは空になります。

## まだできていないこと {#not-there-yet}

- **意味にもとづく記憶。** [実行をまたぐ記憶](./memory) は、以前のテストで確立されたことを単語の一致で呼び出します。関連していても言い回しの異なる規則は、見逃されることがあります。
- **的を絞った無効化。** 新しい証拠は、関係する評価だけでなく、すべての評価を古くなったものにします。保守的ですが、監査は簡単です。
- **何を探るかの選択。** コントローラーが選ぶのはオペレーションです。対象（どの未知事項か、どの予測か）は、条件を満たす最初のものになります。
- **較正。** 較正された予測の確信度はまだありません。`support` は判断であり、測定されるのは予測の実績です。
- **検証された推論。** 推論のラベル（帰納、アブダクション、演繹）は申告されたものであり、形式的な検証器でチェックされてはいません。
- **申告された種類。** 仮説が主張なのか行動の選択なのかは、モデルが仮説を提示するときに申告し、種類のない仮説は提案とみなされます。プロンプトは、世界についての言明を提案と呼ぶことを禁じていますが、それを検証するものはありません。誤ってラベル付けされた主張が、思考者の選好によって確定される可能性があります。
- **選択の背後にある原因の検証。** 目標が何をすべきかを問うものである場合、仮説は行動方針となり、予測が付くのは規則と説明だけなので、そうした目標では結果評価器は使われません。
- **構造化されたチェック。** 制約は自由記述のテキストであり、結論ガードではチェックされません。衝突は、構造化データに対するルールでは検出されません。解決のアクション自体が、事実や仮説を変えることはありません。
