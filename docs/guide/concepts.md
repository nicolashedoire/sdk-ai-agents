# Core concepts

## Overview

SDK AI Agents is a governance infrastructure for AI agents that separates reasoning from action and provides native event sourcing for replay and audit. On top of it, [cognitive agents](./cognitive-agents) add an explicit reasoning layer, and [typed decisions](./typed-decisions) add calibrated, structured answers.

::: info This page covers the foundations
Agents, tools, capabilities, policies, intentions, the event store, traces and replay. They apply to governed and cognitive agents alike.
:::

## Fundamental Concepts

### 1. Agent

An **Agent** is a governed decision-making system that uses an LLM to generate intentions, but all actions go through a controlled Action Engine.

**Characteristics:**
- Minimal configuration (name, LLM model)
- Explicitly declared tools
- Policies for governance
- Versioning for tracking
- Capabilities to organize tools

**Example:**
```typescript
const agent = sdk.createAgent({
  name: 'math-assistant',
  model: 'gpt-4',
  tools: [calculatorTool],
  version: '1.0.0',
  capabilities: ['math']
})
```

### 2. Tool

A **Tool** is an explicitly declared capability that the agent can use. All tools must be registered before use (deny-by-default).

**Characteristics:**
- Mandatory Zod validation schema
- Asynchronous handler
- Versioning
- Association with a capability (optional)

**Example:**
```typescript
const calculatorTool = sdk.defineTool({
  name: 'calculator',
  description: 'Performs basic arithmetic',
  schema: z.object({
    operation: z.enum(['add', 'subtract', 'multiply', 'divide']),
    a: z.number(),
    b: z.number()
  }),
  handler: async ({ operation, a, b }) => {
    // Implementation
  },
  version: '1.0.0',
  capability: 'math'
})
```

### 3. Capability

A **Capability** is a logical group of tools that can be reused across multiple agents.

**Characteristics:**
- Name and description
- List of associated tools
- Versioning
- Optional metadata

**Example (with tool names):**
```typescript
const calculatorTool = sdk.defineTool({ /* ... */ });
const scientificTool = sdk.defineTool({ /* ... */ });

const mathCapability = sdk.defineCapability({
  name: 'math',
  description: 'Mathematical operations',
  tools: ['calculator', 'scientific-calculator'],
  version: '1.0.0'
})

const agent = sdk.createAgent({
  name: 'math-assistant',
  model: 'gpt-4',
  capabilities: ['math']
})
```

**Example (with Tool objects directly):**
```typescript
const calculatorTool = defineTool({ /* ... */ });
const scientificTool = defineTool({ /* ... */ });

const mathCapability = sdk.defineCapability({
  name: 'math',
  description: 'Mathematical operations',
  tools: [calculatorTool, scientificTool],
  version: '1.0.0'
})

const agent = sdk.createAgent({
  name: 'math-assistant',
  model: 'gpt-4',
  capabilities: ['math']
})
```

### 4. Policy

A **Policy** defines the governance rules applied before each action.

**Policy types:**
- **Budget**: Limit on steps or tokens
- **Timeout**: Maximum execution duration
- **Allowlist**: List of authorized tools
- **Custom**: Custom validator

**Example:**
```typescript
sdk.defineGlobalPolicy({
  id: 'max-steps',
  type: 'budget',
  rules: [{
    condition: 'maxSteps',
    action: 'deny',
    metadata: { value: 10 }
  }],
  scope: 'global',
  enabled: true
})
```

### 5. Intention

An **Intention** is a structure generated by the LLM that describes what the agent wants to do, without executing it directly.

**Types:**
- `tool_call`: Call to a specific tool
- `final_answer`: Final answer to the user
- `continue`: Continue reasoning

**Security:**
- All intentions are validated by the Policy Engine
- No direct action from the LLM
- Full traceability

### 6. Event Store

The **Event Store** is the single source of truth for all executions.

**Characteristics:**
- Automatic persistence (JSON files by default)
- Batching for performance
- Full export
- Filtering by type, date, etc.

**Main events:**
- `run.started`: Execution start
- `intention.generated`: Intention generated by the LLM
- `policy.checked`: Policy check
- `action.executed`: Action executed
- `tool.called`: Tool called
- `run.completed`: Execution completed
- `run.failed`: Execution failed
- `run.cancelled`: Execution cancelled

### 7. Trace

A **Trace** is the human-readable representation of a complete execution.

**Content:**
- Event timeline
- Statistical summary
- Final state
- Metadata

**Example:**
```typescript
const trace = await sdk.getTrace(runId)
console.log(trace.summary)
// {
//   totalEvents: 15,
//   duration: 1234,
//   intentionsGenerated: 3,
//   actionsExecuted: 2,
//   policiesChecked: 2,
//   toolsCalled: 2
// }
```

### 8. Replay

**Replay** lets you replay a complete execution without recontacting the LLM.

**Characteristics:**
- Deterministic (same sequence of actions)
- Modifications possible (input, policies, tools)
- Incident debugging
- Non-regression tests

**Example:**
```typescript
const replay = await sdk.replay(runId, {
  input: { message: 'Modified input' }
})
```

## Architectural Principles

### 1. Reasoning/Action Separation

The LLM generates intentions, never direct actions. All actions go through the Action Engine.

### 2. Deny-by-Default

Nothing is authorized by default. All tools must be explicitly declared (registered) before anything can run them.

::: warning Scope of a governed agent
A governed agent can execute **any tool registered in the SDK** that the model names: the agent's `tools` list decides what the model is offered, not what it may call. To keep an agent away from a sensitive tool, register that tool in a separate SDK instance, or deny it with a `custom` policy whose condition matches the tool and whose validator refuses it:

```ts
agent.setPolicy({
  id: 'no-deletes',
  type: 'custom',
  scope: 'agent',
  enabled: true,
  rules: [
    {
      condition: { type: 'condition', conditions: [{ field: 'intention.toolName', operator: 'eq', value: 'delete_customer' }] },
      action: 'deny',
      metadata: { validator: () => false, reason: 'deletions are not allowed for this agent' },
    },
  ],
});
```

Cognitive agents and MCP servers are stricter: they can only run the tools they were given.
:::

### 3. Native Event-Sourcing

Every execution is traceable and replayable thanks to event-sourcing.

### 4. Built-in Governance

Policies are applied structurally, not as an option.

### 5. Full Versioning

Agents, tools, and capabilities are versioned for tracking and traceability.

## Typical Workflow

1. **Initialization**: Create the SDK with the API key
2. **Definition**: Define tools and capabilities
3. **Configuration**: Create the agent with tools and policies
4. **Execution**: Run the agent with an input
5. **Observation**: Review the execution trace
6. **Replay**: Replay for debugging or testing

## Best Practices

### Tools
- Use strict Zod schemas
- Document each tool clearly
- Version tools when they change

### Policies
- Apply reasonable budgets
- Use strict allowlists
- Test policies before production

### Capabilities
- Group tools logically
- Reuse capabilities across agents
- Document capabilities
- **Recommended workflow:** You can pass either tool names (strings) or Tool objects directly to `defineCapability()`. If you pass Tool objects, they will be automatically registered.

### Versioning
- Use semantic versioning
- Document version changes
- Track versions in events

## Security

- **Deny-by-default**: No undeclared tool can be executed
- **Validation**: All inputs are validated with Zod
- **Policies**: Checked before every action
- **Traceability**: All actions are traced
- **Audit**: Replay available for full audit
